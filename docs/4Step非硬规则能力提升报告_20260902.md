# 4Step 非硬规则能力提升报告

日期：2026-09-02

## 结论

当前 TODO 并未全部落地。已有代码已经在 Step1 分段对账、空结果重采、schema 预算、T4 字面量引用提示、T5 汇总口径等方向做了不少补强；本轮又补齐了 T4 target 表存在性查询和 T9 枚举前置注入的一部分。但仍存在几个核心问题：

- Step1 仍偏重：分段、定位、候选扩展、schema 裁剪、LLM 拆解、覆盖自检、fallback 混在一个阶段。
- 一些能力默认关闭或只部分接入，例如 T7 双采样、T8 定向线索重试。
- T12/T13 这类“减少调用次数、降低大输入负担”的结构性优化还没有形成完整主链路。
- 部分实现仍在“修补输出”层面，尚未把 Agent 能力上升到稳定的“计划生成-校验-反馈-再计划”闭环。

如果目标是：不继续堆表名/列名/关键词硬编码，同时提升表、sheet、列名命中率，多指令归纳准确率，并降低整体耗时，建议把优化重心从“失败后补丁”转到“中间表示、候选证据、预算调度、Agent 闭环”四件事。

## 二、核心判断：不要继续强化规则分支

如果继续沿着旧方式做，会自然走向三类局部补丁：

- 某类句子切坏了，就给 splitter 加一个正则保护。
- 某张表经常选错，就给 locator 加关键词/表名权重。
- 某个字段经常丢，就给 Decompose prompt 加特例说明。

这些短期有效，但会慢慢把系统变成“LLM 外壳 + 规则内核”。它的问题是泛化差、不可解释链路长、性能越修越重。

更合适的方向是：让规则只提供结构化证据，不直接替 Agent 做业务判断。也就是说，规则层负责产出 candidate evidence，LLM/Agent 层负责在 evidence 上做归纳、规划、裁决。

## 三、建议的 4Step 架构升级

### 1. Step1 改成两阶段 Planner：Outline → Grounded Plan

现在 Step1 经常一次性承担“切段 + 找表 + 填字段 + 建引用”。建议拆成两个内部子阶段：

第一阶段：Intent Outline

输入原始用户文本，只要求 LLM 输出轻量结构：

```json
{
  "operations": [
    {
      "op_id": "op_1",
      "raw_span": "原文片段",
      "action": "add|set|delete|get",
      "object_summary": "新增兽潮前锋刷新点",
      "mentioned_entities": ["兽潮前锋"],
      "mentioned_values": ["25083001", "320,0,220", "1120"],
      "depends_on": []
    }
  ]
}
```

这一阶段不看全量 schema，不填真实列名，目标只是不漏操作、不切碎语义。这样可以显著降低大输入时的输出负担。

第二阶段：Grounded Plan

对每个 operation，用 locator 的候选证据和压缩 schema 生成可执行 intent：

- table/sheet 选择
- fields 映射
- produces/consumes
- locator field/value

收益：

- 多指令归纳准确率提升，因为第一阶段专注“数清楚有几个操作”。
- 表/sheet/列名准确率提升，因为第二阶段只处理小片段 + 小候选。
- 耗时降低，因为不再让一个巨型 prompt 同时完成所有事情。

### 2. Locator 输出“证据卡”，而不是只输出候选表列表

现在候选表进入 Decompose 时，LLM 看到的是 schema block 和一些信号，但信号之间缺少统一解释。建议让 Locator 产出标准 Evidence Card：

```json
{
  "table": "interaction",
  "sheet": "Interaction",
  "role": "required|dependency|context",
  "score": 0.87,
  "evidence": [
    {"type": "column_signal", "text": "model_id", "column": "模型ID"},
    {"type": "fk_edge", "from": "combat.主怪", "to": "interaction.编号"},
    {"type": "semantic", "reason": "用户描述刷新点/坐标/AI"}
  ],
  "schema_budget_profile": "full|pk_fk_only|name_id_only"
}
```

Decompose prompt 不再塞“无差别候选”，而是明确告诉 LLM：哪些是主目标表，哪些只是依赖表，哪些是背景表。

收益：

- 降低错表率：LLM 不只是看表名，而是看“为什么这张表被召回”。
- 降低 prompt 长度：dependency 表只给 PK/FK/名称列，context 表默认不给完整 schema。
- 更容易 debug：失败时能知道错在证据召回、证据排序还是 LLM 裁决。

### 3. schema 注入改为“按操作局部装配”

当前 schema block 仍偏全局。建议 Grounded Plan 阶段按 operation 装配 schema：

- 与 raw_span 明确相关的 required 表：完整核心列。
- 与 required 表 FK 相连的 dependency 表：只给 PK/FK/名称/被引用列。
- 其它 context 表：不给列，最多给一句用途摘要。

再加一个严格预算器：

- 每个 operation 有独立 schema 字符预算。
- 每次 prompt 记录 `schema_chars`、`candidate_count`、`llm_ms`。
- 超预算不扩大 timeout，而是降级 schema 粒度。

这会比单纯调大 `CODEMAKER_DECOMPOSE_TIMEOUT` 更健康。

### 4. 列名准确率：建立 Column Resolution Agent

列名命中不应完全混在 Decompose 里。建议新增一个轻量 Column Resolution Agent，职责只做：

- 输入：raw_span、候选 sheet 表头、column_signal、value_constraints、enum_mappings、历史别名。
- 输出：字段短语到真实列名的映射候选，带 confidence 和 reason。

示例：

```json
{
  "mappings": [
    {
      "phrase": "坐标",
      "column": "目标位置",
      "confidence": 0.82,
      "reason": "表头附近存在位置/space/model 相关列，历史数据形态支持坐标串"
    }
  ],
  "ambiguous": [
    {
      "phrase": "可交互范围",
      "candidates": ["圆柱高度", "圆柱半径"],
      "needs_user_confirm": true
    }
  ]
}
```

这不是硬规则，因为列选择来自真实 schema、约束、列信号和 LLM 裁决。它能把“字段归属”从通用 Decompose prompt 中拆出来，减少一次大而全的推理。

### 5. Step2 不只 validate，还要能返回 Repairable Plan Diff

Step2 现在更像校验器。建议把 Step2 输出升级成三类结构：

- blocking_errors：必须 ask 或停止。
- soft_warnings：可继续，但 Step4 要透明展示。
- repairable_plan_diff：能自动回灌 Step1/Decompose 的结构化修正建议。

例如：

```json
{
  "repairable_plan_diff": [
    {
      "op_id": "op_3",
      "problem": "literal_fk_missing_target",
      "target_table": "interaction",
      "missing_pk": "25083001",
      "suggestion": "该 FK 引用没有对应 producer，回到 outline 检查是否漏了 interaction add"
    }
  ]
}
```

这样 T4 发现字面量断链后，不只是 warning，而是可以触发一次“局部再规划”：只重跑相关 operation，不重跑整条输入。

### 6. 真正的“双路采样”要放在 plan 层，不放在字段层

当前 T7 双采样是在 `_decompose_single_prompt` 后做，默认关闭，且不是同起点并发。建议改成：

- 只对高风险 operation 触发双路。
- 两路并发生成 Grounded Plan。
- Step2 对两路都做结构化评分。
- 评分维度不写业务规则，只用通用指标：
  - 表/sheet 是否存在
  - fields 是否都在 schema
  - required/PK 是否满足
  - produces/consumes 是否闭环
  - literal FK 是否能命中本批或目标表
  - 字段值是否能按类型/枚举约束通过

最终选择得分高的一路。这样“谁更对”由 Step2 的通用结构化校验决定，不由新规则猜。

### 7. T3 要升级为 Field Shape Rewriter

目前 T3 只是在 `_coerce_value` 失败后问 LLM 如何规整值，但无法真正把值改写到其它列或多列。建议把它前移到 Step2，形成 Field Shape Rewriter：

输入：

- 当前字段
- 当前列类型
- 原始值
- 目标 sheet 前后列窗口
- 全 sheet 表头摘要
- 同列历史值形态

输出：

```json
{
  "action": "rewrite_fields|keep|ask",
  "fields_patch": {
    "坐标X": 320,
    "坐标Y": 0,
    "坐标Z": 220
  },
  "remove_fields": ["目标space ID"],
  "reason": "原值是三元坐标，当前列为单 float，邻近列存在坐标三分量"
}
```

注意：这里不能写“坐标就拆三列”的代码规则。判断必须来自真实表头窗口 + 历史值形态 + LLM 输出。

### 8. 建立 request 级 LLM Budget 和调度器

现在 Step1 budget 更像每次 decompose 局部预算。建议做 request 级预算：

- 整个 Step1 最多 N 次 LLM。
- Outline 固定 1 次。
- 每个 operation 的 Grounded Plan 按风险排序，只给高风险项 LLM。
- 低风险项使用已有 ColumnExtractor / schema exact match / cache。
- 如果预算不足，停止补洞，但把 skipped reason 结构化传给 Step4。

风险排序也不需要业务硬编码，可以用通用信号：

- raw_span 长度
- 候选表数量
- 候选 sheet 数量
- column_signal 是否冲突
- 是否有 FK 链
- 是否有 literal ID 引用
- 是否含多个实体/多个动作

收益是非常直接的：LLM 调用次数可控，慢请求不会无限串行补洞。

### 9. 引入 Plan Cache / Schema Card Cache

很多慢耗时来自重复读取 schema、重复拼 prompt、重复让 LLM 理解相同表结构。建议缓存两类稳定产物：

- TableCard：表用途、业务 sheet、PK、FK、名称列、常用别名、枚举摘要。
- ColumnCard：列名、规范名、类型、值域、历史值形态、是否 PK/FK。

这些都来自已有 xlsx / rules / derived yaml，不是硬规则。Prompt 中优先注入 card，需要细节时再展开完整 schema。

### 10. Step4 反哺不要直接写规则，要写“可审查经验”

Step4 的 anti-pattern 应分两层：

- Session Memory：本次会话后续请求可立即使用，低风险。
- Reviewable Skill Candidate：跨 session 固化前必须经过 promote 门控。

回灌 Step1 时，不要变成“看到某词就选某表”。应该注入为：

```text
本会话已知风险：上一次在多实体刷新点中漏掉了后半字段。处理相似长链时，请先核对 outline 的 operation 数量与原文实体数量一致。
```

这类提示提升 Agent 注意力，不替它做固定判断。

## 四、推荐实施顺序

### 第一阶段：降低 Step1 复杂度

1. 实现 Outline → Grounded Plan 两阶段。
2. 给每个 operation 分配独立 op_id，并贯穿 Step1/2/3/4。
3. Locator 输出 Evidence Card。
4. Decompose 改为按 operation 注入局部 schema。

预期收益：

- 多指令漏拆下降。
- 大 prompt 超时下降。
- Step4 能按 op_id 精确归因。

### 第二阶段：提高表/sheet/列名准确率

1. Column Resolution Agent 独立化。
2. schema block 已引入枚举摘要 `[枚举:...]`，后续可继续接入 enum_mappings 的 label→code 摘要。
3. T3 前移为 Step2 Field Shape Rewriter。
4. T4 已修正为查 FK target 表 PK 集合，后续可升级为 PlanDiffRepair 的局部回灌信号。

预期收益：

- 错列、字段形状不匹配、字面量 FK 断链能在写盘前暴露或修复。
- Step3 partial_write 明显减少。

### 第三阶段：降低耗时并稳定上限

1. request 级 LLM Budget。
2. 高风险 operation 才双路采样。
3. 双路采样真正并发，并由 Step2 通用评分择优。
4. TableCard / ColumnCard 缓存接入主 prompt。

预期收益：

- LLM 调用总数可控。
- p95 延迟下降。
- 复杂请求不会靠长 timeout 硬扛。

### 第四阶段：形成学习闭环

1. Step4 Session Memory 即时回灌。
2. 经验沉淀只进入 reviewable candidates。
3. 用 StepTrace 记录每次请求的候选数、schema 字符数、LLM 次数、失败类型。
4. 后续再接 shadow eval 做默认开关门控。

## 五、关键设计原则

1. 不写表名/列名特判。

所有判断尽量来自真实 schema、relation graph、rules 声明、derived yaml、历史值分布、LLM 结构化输出。

2. 不让规则决定语义。

规则可以召回候选、标证据、算风险、做校验；最终“这句话写哪张表、哪列”应由 Agent 在证据上裁决。

3. 不让 Step3 修计划。

Step3 应继续保持零 LLM，负责执行和写后验证。计划修正应尽量前移到 Step2。

4. 不扩大 timeout 掩盖结构问题。

一旦 prompt 大，优先缩 schema、分 operation、用 card，而不是直接把 timeout 翻倍。

5. 所有 fallback 都要可观测。

任何“产空、丢弃、补壳、重拆、跳过、partial”都要带 op_id、step_id、source、reason，最终 Step4 如实展示。

## 六、最值得优先做的三个改动（A/B/C 已落地，见"一、已基本落地"7/8/9 与"八"）

### A. Outline Planner

这是最核心的准确率提升点。先把用户输入正确归纳为多个 operation，再谈表列映射。它直接对应 TODO 中 T1/T12/T13 的根因。

**落地状态**：已实现 `_llm_outline_operations` + 按 op 回填 `op_id`，接在分段兜底位（非主路径最前）。

### B. Evidence Card + 局部 schema

这是表/sheet/列名准确率和耗时的共同抓手。它能让 LLM 少看噪声、多看证据，减少大 prompt。

**落地状态**：已实现角色标签（`_annotate_schema_role`），尚未实现完整 Evidence Card（逐条 evidence 列表 + schema_budget_profile）。

### C. Step2 Plan Diff Repair

这是把校验结果变成 Agent 能力的关键。Step2 不只是报错，而是生成可局部回灌的结构化 diff，让系统学会“哪里错了，回到哪个 op 修”。

**落地状态**：已实现结构化 diff 输出（`repairable_plan_diff`），尚未接“发现问题→自动只重跑该 op”的回灌闭环。

## 七、一个推荐的新 4Step 流程

```text
Step1 Parse
  1. OutlinePlanner：原文 → operation outline
  2. Locator：operation → Evidence Cards
  3. GroundedPlanner：operation + cards + local schema → executable intents
  4. PlanGraph：统一 produces/consumes/op_id

Step2 Validate
  1. schema / PK / FK / enum / type validate
  2. ColumnResolution 修正低风险错列
  3. FieldShapeRewriter 修正形状不匹配
  4. PlanDiffRepair 局部回灌高风险问题

Step3 Execute
  1. 零 LLM
  2. 按拓扑执行
  3. partial / skipped / write verification 全量结构化记录

Step4 Conclude
  1. 按 op_id + step_id 分桶总结
  2. Session Memory 回灌
  3. Reviewable Skill Candidate 沉淀
  4. StepTrace 慢因与准确率归因
```

这个方向不靠硬编码过某个案例，而是提升 Agent 的输入归纳、证据选择、结构化校验和局部修复能力。短期实现量比继续补正则大一些，但长期会更稳，也更容易把耗时压下来。

### 2026-09-03 第四批：LLM 超时松绑（用户反馈"服务端本来就慢，一直 timeout"）

背景：五.4 原则是"不扩大 timeout 掩盖结构问题"，优先级应是缩 schema/分 operation/用 card。但前序几批已经在做这些结构性工作（分段、局部 schema、候选裁剪），在此基础上仍频繁 timeout，说明当前超时数值本身对真实服务端响应速度偏紧，不是"用长 timeout 掩盖没做结构优化"，而是结构优化到位后数值仍需要匹配真实环境重新校准。

改动文件：

- `server/agent/excel/subagent/base.py`（新增全局比例旋钮）
- `server/agent/excel/subagent/decompose_agent.py`
- `server/agent/excel/subagent/llm_gate.py`
- `server/agent/excel/parse_agent.py`

优化内容：

- 新增 `CODEMAKER_LLM_TIMEOUT_SCALE`（默认 1.0）：`SubAgent._call_llm`/`_call_llm_raw` 统一按比例缩放调用方传入的 timeout，不改各调用点之间的相对大小关系，一个 env 就能整体放宽/收紧所有 LLM 调用超时，不用逐个改数字。做法与既有 `step_ai_enhancer.py` 的 `CODEMAKER_AI_TIMEOUT_SCALE` 同构。
- 直接放宽默认值（真实环境偏慢，光有 scale 旋钮不够，先把基线数值调松）：
  - `CODEMAKER_DECOMPOSE_TIMEOUT`：40→75（decompose 单段/单表 schema prompt 主超时，出现在 `parse_agent.py`/`decompose_agent.py` 共 5 处调用点，全部同步）。
  - `CODEMAKER_DECOMPOSE_CHAIN_TIMEOUT`：90→120（任务链单 prompt 全候选 schema 场景）。
  - `CODEMAKER_DECOMPOSE_BACKFILL_TIMEOUT`：30→45（缺表补漏单表重拆，3 处调用点同步）。
  - Outline Planner 内部固定 `timeout=20`→`30`（原来是硬编码数字，未走 env，现仍是硬编码但数值放宽，且已受上面的 scale 旋钮覆盖）。
  - `CODEMAKER_LLM_THROTTLE_TIMEOUT_S`（全局并发槽等待上限）：60→90，避免单次调用变慢后排队更容易先在这里降级放行、叠加更多并发反而压垮后端。

预计影响：

- 大幅降低"结构已经在优化、但超时数值没跟上真实服务端速度"导致的误报超时/空产出/兜底链路乱触发。
- 用户可用 `CODEMAKER_LLM_TIMEOUT_SCALE` 一个开关做进一步整体调节（如 1.3~2.0），不用记住一堆超时 env 名字。
- 风险：单次调用变慢会让 Step1 总墙钟上升；如果后续要收紧，应先看 StepTrace/`_push_telemetry` 的 `llm_ms` 分布再决定具体数值，而不是拍脑袋改回小值。

测试：`test_decompose_agent.py`/`test_schema_block_budget_wiring.py`/`test_validator_col_disambig_llm.py`/`test_pipeline_v2_e2e.py`/`test_parse_layer.py`（133 passed）+ `test_validator_forward_refs_p13.py`/`test_validator_p9_p14_p27.py`/`test_validator_missing_column_suggestions.py`（32 passed）回归确认改动不影响功能正确性（超时数值改动无法被单元测试直接验证"是否真的不再 timeout"，需要用户在真实环境观察）。

尚未处理（留待后续）：

- Locator/Validator 侧一批更细的固定 `timeout=15/20/25/30`（`locator_agent.py`/`validator_agent.py`/`step_ai_enhancer.py`）未逐个上调基线值，只被新的 `CODEMAKER_LLM_TIMEOUT_SCALE` 间接覆盖；如果这些点也频繁 timeout，需要用户反馈具体是哪个阶段再针对性调。
- 未接入 StepTrace 真实 `llm_ms` 分布来"用数据决定超时基线"，本次调整仍是经验值（如 40→75 是原 90→40 下调前的中间值），后续应看真实分布校准而非再拍一次经验值。
