## 页 3：设计背景与总览 ★

**背景（一笔带过）**：复杂跨表指令（如「封印魔龙」一条指令涉及 8 张表）曾出现耗时 10+ 分钟、调用大模型 23+ 次、漏表严重。根因一句话：**拆分时没有真实表结构信息**。所以核心思路是——**让模型先拿到真实列定义，再按列拆**。

**四步全景**：

```
Step1 解析   定位涉及哪些表 → 按真实列拆成"子任务" → 推断跨表依赖
Step2 校验   写之前检查：列对不对、类型对不对、跨表引用通不通
Step3 执行   按依赖顺序把数据写进表格（纯规则，不调模型）
Step4 汇总   报告结果 + 把失败沉淀成经验，下次更准
```

**一条数据流贯穿全程**：四步之间传的不是自然语言，而是一个结构化对象「子任务」，字段包括：哪张表、哪个工作表、定位列和值、要写的列和值、产出/引用哪些编号。

**大模型只用在两处**：Step1 拆解（1-2 次）、Step4 汇总（1-2 次）。校验字段层和执行阶段都是 **0 次**，全程 **3-5 次**。

> takeaway：模型用在「理解和生成」，不用在「核对和写入」。

# 第二部分：Step1 解析（7 页，核心）

## 页 4：Step1 做什么 —— 三个子组件 ★

Step1 是全链路核心，由三个子组件协同完成，把用户一句话变成"可以直接写库"的一组子任务：

```
ParseAgent（解析智能体）
  ├─ LocatorAgent（定位）     圈出候选表 + 外键扩表（不调模型主路径）
  ├─ DecomposeAgent（拆分）   看着真实列名，把指令拆成"哪张表写哪几列"（唯一调模型处）
  └─ produces 推断（依赖推断）  新编号打"产出"标签，引用处打"消费"标签（不调模型）
```

**完整流程**：

```
① 列名提取    从输入确定性地提出"列名"信号（不调模型）
② 分段        一句话含多个任务时，先切成独立段落（不调模型）
③ 定位        圈出候选表 5-7 张（不调模型主路径）
④ 拉表结构    只拉候选表的真实列定义（并行，不调模型）
⑤ 按列拆分    模型看着真实列名拆（唯一调模型处）
⑥ 依赖推断    按关系图自动推断谁产出、谁消费（不调模型）
```

**六个环节里只有第 ⑤ 步调大模型**，其余全部规则完成。本步大模型调用 **1-2 次**。

> takeaway：把"最难判断的拆分"交给模型，把"机械的定位和拉取"留给规则。

---

## 页 5：LocatorAgent —— 定位涉及哪些表 ★

**职责**：从输入里圈出可能涉及的候选表，供后续拆分使用。

**做法**：

```
① 别名 + 正则 + 关键词扫描输入 → 命中候选表（规则通道）
② 规则没中 → 检索通道（RAG/BM25）补召回（见页 6）
③ 外键扩表：按表关系图广度优先扩 2 跳
   （任务→战斗→奖励，两跳也能扩到奖励表）
④ 歧义时才让模型裁决，否则全程不调模型
```

**双通道定位**：
- 规则通道：别名、关键词，命中率高、不调模型。
- 检索通道：规则没中时，用 BM25 检索补召回，置信度低于规则，**只补充、不压过**。

**配合列名提取前置**：先从输入确定性提取「列名」信号，反向索引反查候选表，信号注入给模型参考——让模型**看着信号选表选列而不是黑盒猜。

> takeaway：快路径走规则，慢路径走检索，模型只在歧义时出场。

---

## 页 6：RAG 定位召回 —— 规则没中时，检索来补 ★（关键技术点）

**要解决的问题**：用户说法千变万化（同义、跨域、生僻词），规则/别名表写不全。比如"测试兽"可能命中不到正确表，纯靠规则会漏。

**做法（`rag_searcher.py`，方法 G）**：

```
① 离线建索引：扫所有表所有 sheet 的去重值 → search_blob（值串）
② 查询时 jieba 分词 + Okapi BM25 打分
③ 召回 top-5 张候选表/表，与规则候选合并（去重）
④ 置信度低于规则 → 只补充、不压过规则结果
```

**关键设计**：
- 索引单例建一次复用，内存态、查询快，不每次重扫。
- `search_blob` 对每个值独立分词（保留值边界），避免"灵兽饕餮"整串成 1 个词导致匹配失败。
- 开关可控：`CODEMAKER_RAG_MODE=bm25|off`，默认开。
- 定位准确率 0.67→0.81 中，RAG 是组成部分——它负责规则命中不到的"语义近邻"。

> takeaway：RAG 不是炫技，是补齐"规则写不全"的召回盲区——快路径走规则，慢路径走检索。

---

## 页 7：DecomposeAgent —— 按真实表结构拆分（核心中的核心）★

**职责**：看着候选表的真实列定义，把指令拆成"哪张表写哪几列"的子任务。

**做法**：

```
① 读候选表所有业务工作表的表头（row1 列名 + row2 类型/别名）
② 把表结构块 + 外键关系 + 填表规则注入提示词
③ 模型产出 JSON 数组，每元素：{表, 工作表, 动作, 字段, 产出, 消费}
④ 解析成子任务列表
```

**这里使用了填表规则（`rules/fill/*.md`）**：
- 项目根 `rules/fill/` 下是用户手写的 Markdown 填表知识（如"item_id 取当前段最大 ID+1、quality 只能填 1-5"）。
- 本步拆分时，加载 `_global.md`（全局）+ 候选表对应的 `<表名>.md`，拼进提示词前缀。
- 作用是**告诉模型怎么生成对的 JSON**：ID 分段取值、枚举归一化、列表格式等，属于"自然语言强约束、给模型读"。
- 只加载命中的候选表规则，避免无关表规则撑爆提示词。

**四条硬约束（写进提示词）**：
1. 列名必须用表里真实存在的列，**不得臆造**。
2. 识别不了的字段标「未知列」，交给后续列匹配器兜底，不硬凑。
3. 本批新产生的编号标「产出」标签。
4. 引用本批其他产出的，标「消费」标签。

**自适应策略（按候选表数量）**：
- 候选表少（≤3）：单次提示词把所有表结构一次给模型，token 省 50-70%，跨表依赖看得全。
- 候选表多（>3）：按表分组并行拆，避免单次提示词过大导致超时。
- 拆分失败 → 回退模板基线兜底，保证不回归。

> takeaway：拆分正确性 = 模型看到的表结构正确性。这是全链路的第一块多米诺骨牌。

---

## 页 8：produces 推断 —— 跨表依赖自动串起来 ★

**要解决的问题**：新数据互相引用。先建任务拿到编号，战斗表要引用它——但拆分时编号还没产生。

**占位符机制**：

```
产出的新编号：标 <产出:新任务ID>
引用它的地方：标 <消费:新任务ID>
```

**谁产出、谁消费，由"表关系图"自动推断**（不调模型）：
- 新增任务 → 产出任务编号 → 战斗表消费它
- 新增战斗 → 产出战斗编号 → 掉落表消费它
- 依赖链自动串起来，执行时按顺序把标签替换成真实编号

**显式主键代换**：产出方如果已有明确主键字面值，直接代入消费方的外键字段，不再等执行期。

> takeaway：跨表依赖交给关系图数据驱动，不靠人记，关键引用一致率 **1.00**。

---

## 页 9：拉表结构 + 分段拆分（工程细节）★

**设计 A：惰性拉取，不全量拉**
- 只对候选的 5-7 张表拉列定义，结果缓存 1 小时（LRU + TTL）。
- 64+ 张表全拉会拖垮速度和 token（词元）消耗；本地冷启动 <3 秒，热缓存命中接近零延迟。

**设计 B：先分段、再逐段拆分（不调模型）**
- 一句话含多个任务时，先切成独立段落，每段单独定位 + 拆分。
- 段内文本短、候选表少、表结构小，模型拆得准、拆得快。
- 某一段拆出 0 条，只对这一小段重跑——便宜，而不是整句话重来。

**设计 C：全局超时保护**
- Step1 整体设时限（默认 60 秒），超时立即冻结当前产出走兜底，不再叠加模型调用。

> takeaway：把大问题切小，失败只重试一小段，超时有保护。

# 第三部分：Step2 校验 + 规则系统（5 页）

## 页 11：Step2 做什么 —— 两层校验 ★

写库之前，检查每个子任务合不合法，不合法的反问用户。**分两层，不能全并行也不能全串行**：

```
字段层（完全并行，0 次模型）
   列存在吗 / 类型对吗 / 必填填了吗 / 值重复吗 / 枚举合法吗

外键层（按依赖顺序推进，0-1 次模型）
   "消费"的编号，必须在本批里已经被"产出"
   引用外部已有数据时，才让模型裁决：新建 / 已存在 / 拼写错
```

**有问题怎么处理**：整理成提示 → 反问用户（改字段 / 改指令 / 跳过）→ 修正后重新校验。

**这里使用了校验规则（`rules/validate/*.md`）**：
- 项目根 `rules/validate/` 下是用户手写的校验约束，写在 Markdown 的 yaml 代码块里，机器解析执行。
- 字段层检查的"类型 / 必填 / 枚举 / 范围 / 唯一 / 主键"这些约束，一部分就来自这里的 yaml 声明。
- 具体消费入口：`type/min/max/unique` 合并进值约束、`required:true` 进必填检查、`enum:[...]` 进枚举白名单、`primary_key` 进主键冲突检测。
- 作用是**机器检查 Step1 产出的 JSON 对不对**，属于"机器可执行的强约束"。
- 用户手写规则优先级最高，覆盖 `skills/` 里自动派生的配置。

> takeaway：字段检查全并行省时间，跨表检查按顺序保正确——两层各管各的。

---

## 页 12：关键设计 1 —— 字段并行 + 外键拓扑 ★

**为什么必须分层**：
- 全并行 → 判断不了"前向引用"：消费方引用的编号还没被产出来，会误报。
- 全串行 → 字段检查失去并行优势，延迟翻倍。
- 折中：**字段层并行，外键层按依赖顺序**，产出集合在推进时即时填充，下游消费方一落地就能校验。

**外键层只调一次模型的场景**：引用的是"外部已存在数据"时，让模型裁决三种情况——需要新建 / 已存在 / 用户拼写错。本批内的引用不调模型。

> takeaway：两段式兼顾了"延迟"和"引用正确性"，这是校验层最重要的一个决策。

---

## 页 13：关键设计 2 —— 失败必有出口 + 只提示不误杀 ★

**设计 A：校验问题必须有出口**
- 所有提示转成"软失败"上报，**保证失败必报告、不静默**。

**设计 B：只提示，不误杀**
- 校验层不直接阻断写库，避免把正确操作误判成失败。
- 硬错误交给执行层的写后校验兜底。

**设计 C：逐项清零校验器的结构性问题**
- 审计出 19 项问题全部清零，典型如：`id` 误匹配成 `model_id`（假阳性）、产出集合收集污染（假阴性）。

> takeaway：校验负责"发现并上报问题"，不负责"粗暴拦截"。

## 页 15：双层规则系统 —— 规则贯穿 Step1 和 Step2 ★（关键技术点）

**要解决的问题**：AI 填表必须有真实业务规则约束，否则自由度太高会填错。这套规则按用途分两类，分别服务 Step1 和 Step2：

```
rules/fill/*.md      填表规则 → Step1：告诉模型怎么生成对的 JSON（自然语言，给模型读）
rules/validate/*.md  校验规则 → Step2：机器检查 JSON 对不对（yaml，机器执行）
```

**① 填表规则（`rules/fill/`，供 Step1 拆分）**
- 纯 Markdown 自然语言，写给模型看。内容：列含义、枚举归一化、ID 分段、默认值、填表格式。
- 拆分时加载 `_global.md`（全局）+ 候选表对应的 `<表名>.md`，拼进提示词前缀。
- 只加载命中的候选表规则，避免无关表规则撑爆提示词。

示例（`rules/fill/item.md`）：
```markdown
- 新增道具时 item_id 必须取当前段最大 ID+1，禁止硬编码。
- quality 品质列只能填 1-5：1凡品/2良品/3上品/4珍品/5绝品。
- 列表列（如 spell_ids）用逗号分隔串，禁止写成 JSON 数组。
```

**② 校验规则（`rules/validate/`，供 Step2 校验）**
- Markdown 文档内嵌 yaml 代码块，机器解析成结构化约束执行。
- 字段层检查的"类型/必填/枚举/范围/唯一/主键"就来自这里。

示例（`rules/validate/item.md`）：
```yaml
tables:
  item:
    ItemBase:
      primary_key: [item_id]
      columns:
        quality:
          type: int
          required: true
          enum: [1, 2, 3, 4, 5]
        item_id:
          type: int
          unique: true
          min: 10000
          max: 29999
```

**关键设计**：
- 同一条业务知识写两处：fill 用自然语言**引导模型填对**，validate 用 yaml 让机器**查对**——生成与校验互相独立。
- 用户手写规则**优先级最高**，覆盖 `skills/` 里自动派生的配置。
- 规则文件改动后重启进程生效，新增表规则只需加一个 `.md`，不改代码。

> takeaway：规则不是写在代码里，是写在数据文件里——AI 的自由度被真实业务规则夹住，不会天马行空。

# 第四部分：Step3 执行（3 页）

## 页 16：Step3 做什么 —— 零模型确定性写库 ★

把校验过的子任务，按依赖顺序真正写进表格。**全程不调模型。**

```
① 按依赖排序   产出的先写，消费的后写，保证引用能接上
② 逐条写入     新增走"构建→校验→预览→提交"，修改/删除直接定位后写
③ 收集结果     独立任务互不影响，失败的记录进失败清单
```

**为什么不调模型**：子任务已经"列名真实、类型匹配、引用闭环"，剩下就是把结构化数据直译成接口调用。让模型进执行环节，只会加延迟 + 引入不确定性 + 打乱引用代换。

> takeaway：模型做判断和生成，不做确定性搬运。

---

## 页 17：关键设计 —— 并行 + 三层兜底 + 真错误 ★

**设计 A：多意图并行**
- 没有依赖的子任务并行写，有依赖的按顺序写。

**设计 B：失败有兜底三层**
- 写后校验修复：写错了自动修，最多 3 轮。
- 失败重规划：整体失败时，模型结合失败原因重新排依赖、再跑一次（最多 2 轮）。
- 断点续跑：中间卡住，从存档点继续，不用重头拆指令。

**设计 C：报错要"真"**
- 报错必须反映真实原因，不能因模型输出的字符串格式问题误判成"列不存在"。
- 只有影响结果的错误才阻塞；独立任务互不连坐。

> takeaway：正常路径零模型；异常路径也有三层兜底，不会写坏就完事。

# 第五部分：Step4 汇总（3 页）

## 页 19：Step4 做什么 ★

**做什么**：把执行结果汇总成报告；有失败时，把失败交给自学习引擎沉淀成经验（下一页详讲）。

```
① 汇总结果    成功清单 + 失败清单（结构化）+ 建议补全方案
② 深度校验    检查跨表引用有没有"指向不存在数据"的悬空引用
③ 自学习      失败 trace → 自学习引擎归纳成"反模式规则"（见页 19）
```

> takeaway：Step4 不只是"报结果"，还负责喂数据给自学习引擎。

## 页 20：自学习引擎 —— 失败沉淀成经验，越用越准 ★（关键技术点）

**要解决的问题**：失败案例"报完就丢"，同类错误反复犯。自学习引擎把每一次失败/成功操作沉淀成规则。

**五类知识都在学习（`skill_updater.py`）**：

| 知识类型 | 来源 | 学成后的作用 |
|---|---|---|
| 列别名 | 用户叫法 → 真实列名 | 下次同类叫法直接命中 |
| 反模式 | 失败操作 / 歧义 / 高频错误 | 拦截或提示同类操作 |
| 表关系共现 | 同一会话连续操作的表对 | 定位时优先扩这些关联表 |
| 修复配方 | 同一错误被同一修复救活 N 次 | 下次同错误走快路径直接修 |
| AI 反模式归纳 | 失败 trace 由 LLM 批量归纳 | 同类失败自动预防 |

**每个规则都过"安全阀"才生效（promote_with_guard）**：

```
候选规则 → 快照 → 写盘 → 跑小回归测试 → 不达标 → 回滚 + 进隔离区
                                         → 达标   → 正式生效
```

**规则生命周期管理**：
- 状态三态：`active`（生效）/ `pending_review`（待审核）/ `dormant`（休眠）。
- 权重衰减：60 天不使用移除、权重 <0.3 降休眠、≥0.3 保生效——防止规则无限膨胀。
- AI 归纳的规则先进"暂存区"（不进版本库），达阈值才合并进正式文件——防止模型噪声污染人工策展的规则。

**安全阀的意义**：自学习最容易学偏、过拟合到错误场景；快照→回归→回滚→隔离这条链保证"学错了能撤、坏了不扩散"。

> takeaway：自学习不是"失败就学"，是"学习 → 验证 → 门控生效"，安全地越用越准。
