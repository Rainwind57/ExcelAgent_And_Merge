# ExcelAgent 后续优化路线

本文档记录当前 4-Step Excel-Agent 在最新代码合并后的后续优化方向。目标不是针对单个样例硬编码，而是提升 Agent 面对真实策划输入时的结构化理解、校验修复、执行稳定性和经验沉淀能力。

## 1. 当前判断

最新代码继续沿着正确方向增强：让 LLM 负责语义理解，让代码层负责 schema-aware 编译、规则校验和确定性执行。

这类架构比单纯堆 prompt 更稳，因为 Step1 输出一旦错误，Step2/Step3/Step4 都会被拖下水。后续优化应优先保证 Step1 JSON 的可执行性，再让 Step2 做可恢复的交互修正，而不是让 Step2 被迫兜底所有语义错误。

## 2. Step1：从“拆 JSON”升级为“语义计划编译”

后续重点是把 ParseAgent / LocatorAgent / DecomposeAgent 的职责边界继续拉清楚：

- LocatorAgent 负责召回候选表，但不能让弱 alias 命中过度挤掉真正主语表。
- DecomposeAgent 负责在真实 schema 下生成 intents，不能伪造字段、表名、占位符或 resolved_from 占位。
- ParseAgent 负责把 LLM 输出编译为可执行计划，包括目标表归一、字段映射、空壳删除、影子行去重、依赖检查和 FK 修复。

建议继续增强 semantic plan：

- 为每个自然语言片段保存主语、动作、对象、数量、字段和值。
- 对“再把它绑定”“前面的活动”“这几个奖励”等跨段引用建立上下文链。
- 对新增实体生成稳定 entity key，再映射到 produces/consumes，占位符只作为执行层协议出现。
- 对同一实体的多表配置做分组，避免 LLM 输出稀疏重复 intent。

## 3. 候选表定位优化

当前复杂样例失败常见原因是候选表召回过宽或主表被挤出。后续可以加入更细的排序信号：

- 动词邻近度：新增、配置、绑定、修改等动作附近的名词权重大于远距离 alias。
- 实值字段命中：片段中出现的字段值能落到某表真实字段时，提高该表得分。
- FK 闭包层级：直接承载动作的表优先，其直接 FK 目标次之，远端辅助表降权。
- 表角色识别：主实体表、等级表、绑定表、奖励表、文本表应有不同默认角色。
- 噪声抑制：只因 column_reverse 或弱别名命中的表，不应进入高优先候选。

这部分不要写业务词特判，可以把信号做成通用 scorer，并在测试里覆盖不同资源域。

## 4. FK 与占位符策略

FK 和占位符仍然是多表新增任务的核心契约，建议保留，但要收敛使用边界：

- 已存在资源能唯一匹配中文名时，直接解析为真实 ID。
- 本批次新增实体被后续引用时，使用 placeholder。
- placeholder 必须有 producer，producer 必须在正确目标表。
- 禁止 LLM 输出 `<resolved_from_xxx>` 这类内部修复占位。
- Step2 必须阻断悬空 placeholder、错表 placeholder、自产自消和依赖环。

长期方向是让 LLM 输出 entity reference，代码层再编译成 placeholder。这样能减少模型随意编 placeholder 名称导致的连锁失败。

## 5. Step2：从错误提示升级为可恢复编辑

Step2 的价值不只是报错，而是让用户能够修正并续跑。

建议实现全字段可编辑表格：

- 每个失败 intent 展示目标表、动作、所有字段和值。
- 用户可改列名、改值、删除字段、删除整条 intent。
- 提交后后端把编辑结果回写到原 intent，并重新跑 Step2。
- 不允许“确认后直接绕过硬错误”进入 Step3。
- 修正记录应进入 Step4，作为后续经验沉淀来源。

这样可以解决“前端确认后 Step3/Step4 仍报错”的问题：确认不是跳过校验，而是产生新的可校验 intent。

## 6. Step3：执行层保持确定性

Step3 不应承担语义猜测职责。后续应强化执行前契约：

- 进入 Step3 前必须保证 schema、字段、类型、枚举、FK、placeholder 全部通过。
- 写盘按依赖拓扑排序执行。
- 新增主键分配和 placeholder 回填必须有审计日志。
- 一旦部分写入失败，要能定位到 intent、sheet、字段和值。
- 对 PK 冲突、必填缺失、资源文件缺失等错误分类返回，而不是泛化成执行失败。

Step3 越确定，Step1/Step2 的边界就越清楚。

## 7. Step4：总结与经验沉淀

Step4 应从结果摘要升级为学习闭环：

- 总结新增、修改、删除了哪些表和行。
- 记录系统自动修复动作，例如字段映射、FK 名称解析、影子行去重。
- 记录用户手动修正，形成字段别名、枚举别名、表定位偏差等候选经验。
- 对失败样例归纳反模式，例如跨段代词、省略主语、弱 alias 误召回、必填字段缺失。
- 将高置信经验写入 rules / examples / retrieval，而不是直接写死到代码。

经验沉淀需要版本化和置信度，避免一次错误修正污染后续所有任务。

## 8. 评测体系

后续评测不应只看单样例是否跑通，而要建立分层指标：

- Step1 JSON 指标：表命中率、字段命中率、幻觉字段数、空壳 intent 数、placeholder 正确率。
- Step2 指标：硬错误数、可自动修复数、需要用户确认数、误报率。
- Step3 指标：写盘成功率、PK 冲突率、FK 悬空率、半写入恢复能力。
- Step4 指标：摘要完整度、修复记录完整度、经验可复用率。
- 端到端指标：planner_style、complex_task_chain、complex_task_chain_extra 连续多轮 LLM 稳定性。

建议保留 DeepSeek / codemaker 两套底座回归入口，用同一批 cases 对比模型差异，区分“代码问题”和“模型能力问题”。

## 9. 下一阶段优先级

1. 实现 Step2 全字段可编辑回写，确保用户确认后重新校验再进入 Step3。
2. 增强复杂链路上下文继承，解决“前面那个/这几个/再绑定”等跨段引用。
3. 把 entity reference 编译为 placeholder，减少 LLM 直接控制占位符协议。
4. 优化候选表 scorer，避免弱 alias 表挤掉真实主语表。
5. 建立 Step1 JSON 审计报告，将失败原因固定为可统计指标。
6. 将 Step4 修复经验沉淀为可审查规则，而不是隐式 prompt 增量。

## 10. 结论

ExcelAgent 的核心能力建设路线应是：

LLM 理解自然语言，代码层编译语义计划，Step2 做可恢复校验，Step3 确定性执行，Step4 形成经验闭环。

这个方向能覆盖更多真实输入，比针对 planner_style 或 complex_task_chain 单点补丁更可靠，也更适合作为答辩中的技术主线。
